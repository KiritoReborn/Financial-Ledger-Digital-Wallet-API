# B03 idempotent transfer endpoint (AI-assisted)

**Goal.** Expose `POST /transfers`: move simulated funds from the caller's
wallet to any user's wallet of the same currency, safely repeatable with an
`Idempotency-Key`.

**What was built.** `backend/app/api/transfers.py` handles the request in one
`BEGIN IMMEDIATE` transaction. It checks the bearer token (401) and the key
(400 or 422), then calls `run_idempotent` from
[[projects/2026-11-25-b01-idempotency]] with scope `TRANSFER` and no target ID.
The operation lives in `backend/app/services/transfers.py`. It checks that the
sender exists (404) and belongs to the caller (403), that the wallets differ
(422) and that the receiver exists (404). It then posts a `TRANSFER` with C04's
`LedgerPoster`, which returns `CURRENCY_MISMATCH`, `INSUFFICIENT_FUNDS` or
`VALIDATION_ERROR` for a system wallet. The response is the OpenAPI `Transfer`,
status 201, with `Idempotent-Replayed: true` or `false`.

**Decisions.**
- The ownership checks run inside the idempotent operation, so any rejection
  rolls back and stores no key (FR-2.9).
- Keys are unique per user and operation in Migration 001. A deposit key and a
  transfer key with the same text do not conflict.
- An omitted `description` and an explicit `null` give the same fingerprint, so
  either form replays.

**Evidence.** `backend/tests/test_transfers.py` has 56 tests through the real
`POST /users`, `POST /wallets` and deposit routes. They cover:
- the response shape, balances, one debit and one credit entry, and a clean
  `GET /admin/reconcile`
- insufficient funds, currency mismatch, same wallet, and system wallets as
  sender or receiver
- sending from another user's wallet (403), unknown wallets (404), bad tokens (401)
- replay, conflict on a changed amount, description or receiver, and keys scoped
  per user and per operation
- strict integer amounts, malformed and non-v4 UUIDs, unknown fields, and
  over-long descriptions (TQ-4, TQ-6)
- a rejected transfer storing no key, then the same key succeeding once funded

Every rejection is checked to leave the wallets, transactions, entries and keys
unchanged.

**Shared-file changes.** Two lines in `backend/app/main.py` register the router.
One line in `backend/tests/test_api_health.py` adds `/transfers` to the expected
paths.

**What to watch.** `GET /transfers/{id}` is C06 (Member C). The 50 competing
transfers over HTTP are Stage 5 (B04).
