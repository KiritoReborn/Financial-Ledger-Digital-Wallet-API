# B02 idempotent deposit endpoint (AI-assisted)

**Goal.** Expose `POST /wallets/{id}/deposit`: credit simulated funds to the
caller's own wallet, safely repeatable with an `Idempotency-Key`.

**What was built.** `backend/app/api/deposit.py` handles the request in one
`BEGIN IMMEDIATE` transaction from the shared provider. It checks the bearer
token (401), then the key (400 missing or blank, 422 invalid), then that the
wallet exists (404) and belongs to the caller (403). It then calls
`run_idempotent` from [[projects/2026-11-25-b01-idempotency]], which either
replays the stored response or posts a `DEPOSIT` with C04's `LedgerPoster`:
debit the system wallet of the wallet's currency, credit the caller's wallet.
The response is the OpenAPI `Transaction` with both entries, status 201, and
`Idempotent-Replayed: true` or `false`. The amount must be a strict integer from
1 to 10^12, so `10.5`, `"100"`, `true`, zero and negative values give 422.

**Evidence.** `backend/tests/test_deposit.py` has 35 tests through the real app
and `POST /users`. They cover:
- the response shape and both entries
- the system wallet chosen by currency (INR and JPY)
- a clean `GET /admin/reconcile` after deposits
- replay with an identical body, conflict on a changed amount or wallet, and keys
  scoped per user
- every 400/401/403/404/422 case, each checked to change nothing
- a failed deposit storing no key, then the same key succeeding once the cause is fixed

**Shared-file changes.** Two lines in `backend/app/main.py` register the router.
One line in `backend/tests/test_api_health.py` adds the deposit route to the
expected list of API paths.

**What to watch.** Member A's wallet routes and start-up system wallets (H05,
FR-1.9) are not on main yet, so the tests insert wallets directly. Until then, a
deposit in a currency with no system wallet returns 500 and stores nothing.
