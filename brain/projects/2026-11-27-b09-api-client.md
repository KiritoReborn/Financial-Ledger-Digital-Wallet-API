# B09 secure API client and deposit/transfer guide (AI-assisted)

**Goal.** Give people and the B06 `simulate-transfer` skill one safe way to
call the deposit and transfer API without ever exposing a token (NFR-SEC-7).

**What was built.**
- `scripts/api_client.py`, standard library only. `LedgerClient.from_env()`
  reads `API_BASE_URL`, `LEDGER_TOKEN`, `ADMIN_TOKEN` and `ADMIN_KEY`. Helpers
  cover health, register, wallets, deposit, transfer and reconcile, and there is
  a matching command line.
- `docs/deposit-transfer.md`, a user guide with placeholder values only.

**Decisions.**
- *Keys.* Every deposit and transfer gets a new UUID v4 `Idempotency-Key`
  unless one is passed. The key is returned with the result so a caller can
  retry with it after a timeout. The client never retries on its own.
- *Secrets.* Tokens travel only in the `Authorization` header, and are never in
  URLs, bodies, exceptions, `repr` or output.
- *Token file.* `register` on the command line writes the new token to a new
  file and prints a placeholder instead.
- *Transport.* Tokens go only over HTTPS, or plain HTTP to localhost.
  Credentials, a query or a fragment in `API_BASE_URL` are refused.
- *Local checks.* A missing token or a malformed wallet ID is refused before
  anything is sent, so no request is made with a half-built URL.

**Evidence.**
- `backend/tests/test_api_client.py` has 30 tests through the real app. They
  cover:
  - every helper
  - replay with a returned key, and conflict
  - API errors carrying status, code and request ID
  - local refusals and unsafe base URLs
  - an unreachable API
  - a recorded check that secrets appear only in the `Authorization` header
  - the command-line register, deposit, transfer, reconcile and error paths
- A live run against uvicorn on a temporary database went through the command
  line: register, wallets, deposit, transfer, replay, insufficient funds and
  reconcile. No token or admin secret appeared in any output.
